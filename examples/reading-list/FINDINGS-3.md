# API ergonomics findings, round 3

The reading list rebuilt on core after the round-two issues ([ISSUES-2.md](./ISSUES-2.md)) landed. Item numbers in the scorecard match [FINDINGS-2.md](./FINDINGS-2.md). New findings continue from 27.

## Verdict

This is the best round yet. Collections make the typed surface feel like the default: `client.collection(Book)` gives one object whose every verb takes and returns `BookContent`, with a single signature each. The app has no casts, no re-read helper, and no hand-written types beyond the interface names. Compile errors are now one line that names the typo. Handles carry their lineage, migrations are declared steps checked when the app starts, and a page of books survives a record the app can't read.

The rough edges have moved. They're no longer about how far the typing reaches. They're about **migrations**: what a step choice does to later queries, and what one bad record does to `migrateAll()` (27–29). The app is about the same size as last round, but none of the code is workarounds any more.

The prototype in `src/collection.ts` is gone. Its tests now run against core's `Collection` in `tests/reading-list.test.ts`, on both adapters (46 tests).

## New findings

### Worth fixing

27. **One bad record blocks `migrateAll()`, and the README pattern turns that into a failed startup.** A `derive()` step can produce a value the target refuses: here, a `@1` book whose free-text status was `'meh'`. Reading it through the collection works: it comes back with `status: 'meh'`, typed as an unlisted value. But `migrateAll()` aborts on it with `Content validation failed: status: Expected one of …`, and the message doesn't name the record. `installReadingList()` calls `migrateAll()`, as the README's `install()` does, so the app can no longer install or upgrade until someone finds that record. Patching it through the `Book` collection fails the same way, since the patch migrates first. The only fix is a patch through the `BookV1` collection, which nothing points to. Suggestions: name the record ID in the failure, offer a mode that reports failures and carries on (as a query reports misfits), and say in the error that the record can be repaired at its stored version.
28. **`derive()` returns `unknown`.** Its input is typed, but its output isn't checked against the target field, so `derive('status', (c) => c.status)` compiles even though `c.status` is free text and the target is an enum. That's how 27 gets in. Typing the result as the target field's write type (`BookContent['status']`) would make the compiler require the mapping to be total. The schema checker already refuses a string → enum `map()`, so the gap is only in the escape hatch.
29. **A migration step decides which records later queries can see.** `map()` can't turn free text into an enum (`"status" changes kind from string to enum`), so this migration had to use `derive()`. Per the spec's translation table, `derive()` narrows: until `migrateAll()` runs, `listBooks({ status: 'finished' })` silently leaves out a `@1` book that reads as finished, and says so only through `skipped.older` on the first page. Sorting by `title`, which no step touches, still includes it. This behaviour is documented and principled, but the consequence is far from the cause: the choice is made in `schema.ts` and shows up as missing rows in a list view. The `migration()` call site could warn that a step narrows queries, and the README's `onShelf()` example checks `misfits` but not `skipped`.

### Smaller

30. **A content sort or filter hides newer versions without listing them.** An unfiltered `query()` lists a `@3` book in `misfits`. Add `sort: { contentField: 'title' }` and the same book disappears, with only `skipped.newer: true` on the first page. The spec says this deliberately (a newer version can't be translated), but it means a list view's "you need to upgrade" banner depends on which sort the user picked. An app wanting a reliable count has to run a second, unfiltered query.
31. **Single-element edits are wordy.** Tagging went from `associate(id, [tag])` to `editAssociations(id, [{ op: 'add', association: { kind: 'tag', label } }])`, and the two-permission grant in `letEdit` is now six lines. Having one edit shape for associations and access is good, but the common case of adding one thing carries the most ceremony. Small `add(…)`/`remove(…)` edit builders (as `map()`/`rename()` are for steps) would help.
32. **An installed app needs a system-type request to upload files, and nothing says so.** The README manifest maps each app type to grants. An app built that way fails `putAttachment()` with `No create grant for type "_attachment@1"`. Adding `{ baseId: '_attachment', actions: ['create', 'read-own'] }` fixes it, and `planInstall()` shows it as a foreign request with `owner: 'system'`, which is right. Worth a line in the README and in `docs/spec/apps.md`.
33. **`InstallRequest.actions` is a mutable array.** Built inside a spread (`requests: [...types.map(…), extra]`), the literal widens to `string[]`, and `as const` is then rejected because the result is `readonly`. The fix is an explicit `(h): InstallRequest =>` annotation. `readonly GrantAction[]` in the type would accept both spellings.
34. **`collection(Book)` loses the interface name.** `client.collection(Book)` is `Collection<ContentOf<…>>`, so hovers and errors show the expanded object even after you've declared `interface BookContent`. Annotating the field as `Collection<BookContent>` restores the name. This is fine once you know, and the README's `Library` does it, but the inferred type doesn't benefit from the advice.
35. **History is untyped and lives on the client.** `getVersions()` and `getJournal()` aren't on `Collection`, so `history()` still reaches past it to `StackClient`, and `RecordVersion.content` is `Record<string, unknown>`. Versions can sit at older type IDs, so typing them isn't straightforward, but a collection that already migrates on read could offer the same for snapshots.
36. **A collection can't be opened on a version the process has no migration into.** `stack.collection(BookV3)` throws `No migration from "…book@2" to "…book@3" was passed to Stack.open()`, even just to `create()`. That's right for an app, which always ships its chain. It only surfaced here while simulating a newer build in one process (the tests write `@3` untyped), so it's noted for test authors rather than as a defect.
