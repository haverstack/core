A subject's signed delegation can let an app act for them. A `Session` is an `Actor` with an optional `delegationChain`; `TokenSession` is one with `principalId` populated, and both `asActor(session)` and `StackTokenStore.createToken(session)` take it. `Stack.open(adapter, { verifyDelegation })` takes the verifier that validates a chain, and a delegated view validates it on every operation through `Stack.verifyDelegationChain(chain, { principalId, subjectId })`, with the stack's own revocations, throwing the new `DelegationRefusedError` (an authentication failure, answered with 401) for every refusal, a stack without a verifier included. A refused delegation ends a subscription. A verified delegation names its families, each with the verbs allowed on it, and counts on the principal's side of the permission check beside grants naming the principal, evaluated as a grant would be (write implies read); it never reaches an ungrantable family. `verifyAuthChallenge()` takes a `verifyDid` callback that, when given, decides every DID. A `DidCredential` may carry a `delegationChain`, and `parseAuthTokenBody()` reads one. New `_revocation@1` system type, ungrantable and owner-written: `Stack.revokeDelegation(chain, { actor })` writes one naming the chain's last delegation, admitting the owner or an issuer of a link acting as itself, and `ScopedStack.revokeDelegation(chain)` calls it for the session's key; both are present only on a stack opened with a verifier. `Stack.isDelegationRevoked(cid)` answers whether one names a delegation, and `parseRevocationBody()` reads `POST /revocations`. New exported types: `Session`, `VerifiedDelegation`, `DelegationCheck`, `DelegationVerifier`, `RecordVerb`, `DidSignatureVerifier`, `RevocationContent` and `WireRevocationRequest`.
