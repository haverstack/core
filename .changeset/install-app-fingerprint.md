Every install apply names the plan it approves. `installApp(manifest, { did, fingerprint })` replaces `installApp(plan)`: it plans the manifest again for `did` and refuses with `StackConflictError` unless the result is the plan whose `fingerprint` it was given, so a server that shows the owner a plan in one request and applies it in another checks the approval exactly as an in-process caller passing `plan.fingerprint` does. `InstallPlan` carries that `fingerprint`: a SHA-256 over the plan the owner sees, in canonical form — schemas by `schemaHash`, every list as a set — with no Record's `version` in it, so neither a reordering store nor an edit no plan shows makes an approval stale. `planInstall()` refuses a manifest requesting a family twice, as it refuses a type listed twice. An action list is a set written without repeats: `grantType()`, a `_grant` write, a manifest's requests and an `_install` write all refuse an action named twice with `StackValidationError`; a stored list is still read as a set. `InstallAppOptions` is exported from `@haverstack/core`.
